当一个模型大到单张 GPU 根本塞不下时，怎么在成百上千张 GPU 上训练它？本节课以 **Llama 3-405B** 为贯穿案例。Meta 在论文里公开了大量训练基础设施细节，非常难得——因为 GPT-4 之后的趋势是各大公司对训练细节守口如瓶。

---

## 整节课的脉络

这节课分成两半：前半段讲硬件（GPU 里面长什么样、集群怎么搭），后半段讲算法（四种并行策略怎么排兵布阵）。两半缺一不可——不理解硬件瓶颈，就不会理解为什么需要这么多种并行策略。

## 硬件篇：GPU 内部结构与集群拓扑

### NVIDIA H100 长什么样

![H100 GPU 核心](/images/lec11_h100_die.png)

GPU 最初是为图形渲染设计的，但现在已经是通用的并行计算处理器。H100 的结构很直观：中间是一大块计算核心，周围环绕着 80GB 的 HBM（高带宽内存）。

关键数据：
- HBM 到计算核心的带宽：**3352 GB/秒**
- 内存和计算单元是分离的，通过总线交换数据

这个"内存与计算分离"的架构是后续所有并行策略的物理背景——**GPU 内部带宽极高（3TB/秒），但 GPU 之间的通信带宽就低得多**。

### 深入到计算核心

![H100 计算核心](/images/lec11_h100_sms.png)

放大计算核心，最中央是 50MB 的 L2 Cache，周围分布着 **132 个流式多处理器（SM, Streaming Multiprocessor）**。实际上芯片上有 144 个 SM，但出于良率考虑，NVIDIA 只保证至少 132 个可用。

每个 SM 是一个独立的并行计算单元——你可以把它想象成一个简化版的 CPU 核心，带有向量指令能力。相比 CPU，SM 的并行性更强，但时钟频率更慢。

### 单个 SM 内部：FP32 核心与 Tensor Core

![SM 内部结构](/images/lec11_h100_sm_inside.png)

继续放大，每个 SM 内部有什么？

**存储层次：**

- 256KB L1 Cache + 256KB 寄存器文件
- 延续了经典的内存层次结构：离计算越近，读写越快，但容量越小；离计算越远，容量越大，但访问越慢。

**FP32 核心（通用计算）：**

- 128 个 FP32 核心
- 每个时钟周期完成一次 $a \times x + b$（乘加融合，2 次浮点运算）
- 一个 SM 每时钟周期：$128 \times 2 = 256$ 次 FP32 浮点运算

**Tensor Core（矩阵加速）：**

- 4 个 Tensor Core，通过专用电路计算分块矩阵乘法
- 一次 $AX + B$，其中 $A$ 是 $16 \times 4$ 矩阵，$X$ 是 $4 \times 8$ 矩阵，$B$ 是 $16 \times 8$ 矩阵
- 一个 Tensor Core 每时钟周期：$16 \times 4 \times 8 \times 2 = 1024$ 次浮点运算
- 4 个 Tensor Core 合计：**4096 次/时钟周期**

这里有一个关键细节：Tensor Core 使用**混合精度**——16 位低精度输入，32 位高精度输出（BF16 → FP32）。实际训练中如果不小心用了 FP32 张量，就会回退到 FP32 核心上计算，速度会慢 15 倍以上。

**一个 SM 每时钟周期的总算力：4096 + 256 = 4352 次浮点运算。**

按 BF16 精度算，一块 H100 SXM 的理论峰值是 **1,979 TFLOPS**——这是训练时实际瞄准的算力目标。

### GPU 性能的代际跃迁

从 K40 到 H100，FP32 算力增长不算夸张（5 → 67 TFLOPS），但 Tensor Core 的出现让 BF16 算力直接跳到接近 2000 TFLOPS。本质原因是：**矩阵乘法是神经网络 99% 的计算量，Tensor Core 用专用硬件把这个操作做到了极致。**

### 从一张 GPU 到一座集群

![GPU 服务器](/images/lec11_gpu_server.png)

一张 H100 内部的带宽是 3352 GB/秒。但当我们把 8 张 H100 放进一台服务器：
- 通过 NVLink/NVSwitch 互联
- GPU 之间的带宽：**900 GB/秒**

从 3TB 掉到 900GB——已经差了近 4 倍。

![集群拓扑](/images/lec11_cluster_topo.png)

继续往外扩，以 Meta 的 Llama 3 训练集群为例：

| 层级 | GPU 数量 | GPU 间带宽 |
|------|---------|-----------|
| 单 GPU | 1 | 3,352 GB/秒 |
| 服务器（8 GPU） | 8 | 900 GB/秒 |
| 机架（2 服务器） | 16 | — |
| Pod（192 机架） | 3,072 | 50 GB/秒 |
| 集群（8 Pod） | **24,576** | < 50 GB/秒 |

整个集群的恐怖数字：1.875 PB 总显存，415M FP32 核心，13M Tensor Core，理论峰值 24.3 EFLOP/秒。

**一个核心设计原则：** 把通信量大的操作放在高速链路上（服务器内部 NVLink），尽量减少跨节点、跨 Pod 的通信。

### 其他训练芯片

Google 的 **TPU v5p**：每芯片 459 TFLOPS BF16、95GB 显存，以 8960 芯片的 Pod 为单位部署。AMD 的 **MI325X**：1300 TFLOPS BF16、256GB 显存。AWS 的 **Trainium2**：667 TFLOPS BF16、96GB 显存，64 芯片组成 UltraServer。

## 算法篇：四种并行策略

![四种并行策略总览](/images/lec11_four_axes.png)

一个 Transformer 模型操作的是形状为 `(Batch, Sequence, Dim)` 的张量，有 L 层。这四个维度自然引出了四种切分策略：

| 策略 | 切分轴 | 思路 |
|------|-------|------|
| 数据并行 (DP) | Batch | 不同 GPU 处理不同数据，同步梯度 |
| 上下文并行 (CP) | Sequence | 不同 GPU 处理长序列的不同段落 |
| 流水线并行 (PP) | Layers (L) | 不同 GPU 拥有不同层 |
| 张量并行 (TP) | Hidden Dim | 同一层内的权重矩阵分块计算 |

---

## 数据并行 (DP)

### 基本思路

![数据并行步骤](/images/lec11_dp_steps.png)

数据并行是最直观的策略。损失的梯度是线性的：

$$\nabla_W L(W) = \frac{1}{M} \sum_{m=1}^{M} \underbrace{\left( \frac{1}{N} \sum_{i=1}^{N} \nabla_W \ell(x_{m,i}, W) \right)}_{\text{局部梯度 } g_m}$$

步骤拆解：

1. 每个 GPU 维护一份完整的模型权重副本
2. 各 GPU 加载不同的 mini-batch 数据
3. 各自独立前向传播，计算局部损失
4. 各自独立反向传播，计算局部梯度
5. **All-reduce**：每个 GPU 把自己的梯度发给所有其他 GPU，同时收集其他人的梯度，取平均
6. 各 GPU 用平均梯度更新权重——所有 GPU 再次拥有完全相同的权重副本

步骤 4 和步骤 5 **可以重叠**——反向传播一算出一部分梯度就开始通信，不需要等全部算完。

### 异步 SGD

有一种变体叫异步 SGD：每个 GPU 隔一段非固定时间再交换梯度，不等所有人。理论上减少了等待时间，但实践中非常不稳定，难以调试和复现。**同步计算是主流选择。**

### DP 的硬伤

DP 要求每个 GPU 都能装下完整模型。以 H100 的 80GB 为例：
- 每个参数需 2 字节（BF16）
- Adam 优化器需要额外存储：参数本身 + 一阶动量 + 二阶动量 + 一个缩放因子 ≈ 每参数 8 字节
- 所以 10B 参数的模型光权重和优化器状态就要约 80GB——**正好塞满一张 H100**
- Llama 3 有 405B 参数……

DP 的单 GPU 显存瓶颈直接催生了 FSDP。

## 全分片数据并行 (FSDP)

### 核心思想

![FSDP](/images/lec11_fsdp.png)

FSDP = Data Parallelism + ZeRO 分片。关键洞察：**每个权重 $W_i$ 只属于一个 GPU**，这个 GPU 同时负责该权重的梯度和优化器状态。没有任何 GPU 在任何时刻持有完整模型。

### 逐层算法

**前向传播：**

1. 拥有第 $i$ 层权重的 GPU 将其 **all-gather**（广播）给所有 GPU
2. 所有 GPU 用自己的本地数据计算该层的激活值
3. 所有 GPU **丢弃**不属于自己的权重分片（释放显存）
4. 与此同时，下一层权重的拥有者已经在广播第 $i+1$ 层的权重——**预取**，通信与计算重叠

**反向传播（逆序执行）：**

1. 权重拥有者再次 all-gather $W_i$
2. 所有 GPU 计算局部梯度
3. **Reduce-scatter**：梯度被聚合，但每个拥有者只收到自己负责的那部分梯度
4. 拥有者在本地执行优化器更新（因为它本来就持有优化器状态）

直觉：FSDP 相当于在每一层做一个"借还"操作——前向时借来所有权重，算完就还；反向时再借一次，算出梯度后把归约后的梯度还给各自的主人。

### 关键优化

- **预取（prefetch）**：算第 $i$ 层前向的时候，同时拉第 $i+1$ 层的权重
- **最后一层不丢弃**：前向算完最后一层后保留权重，因为反向马上需要——省一次 all-gather
- **激活值仍然占用显存**：FSDP 只分片了权重和优化器，激活值没有分片。以 Llama 3-405B 的 FFN 为例：hidden_dim=16384, 126 层, BF16, batch=1, seq=4096 → 激活值仍然很大

## 混合分片数据并行 (HSDP)

![HSDP](/images/lec11_hsdp.png)

FSDP 每层需要 3 次集合通信（前向 all-gather + 反向 all-gather + reduce-scatter）。当 GPU 数量很大时，这成了通信瓶颈。

HSDP 的思路是把 $N$ 个 GPU 排成 $M \times K$ 的网格：
- **组内 K 个 GPU**：做 FSDP，权重完全分片——通信量大，但走的是快速节点内链路
- **组间 M 个组**：做普通 DP——只在梯度同步时做一次 all-reduce，走慢速跨节点链路

本质是把 FSDP 的重通信限制在高速链路内，跨节点只做轻量的 DP 同步。

---

## 激活检查点 (Activation Checkpointing)

FSDP/HSDP 解决的是权重和优化器的显存问题。但激活值才是更大的隐形杀手——大 batch × 长序列时，激活值比权重还占地方。

### 问题建模

每一层有两个函数：
- 前向：$A_{i+1} = F_i^{\rightarrow}(A_i)$，需要存储 $A_i$ 供反向使用
- 反向：$G_i = F_i^{\leftarrow}(A_i, G_{i+1})$，需要 $A_i$ 来计算梯度

假设 N 层，每层计算量和存储量都是 O(1)：

| 策略 | 时间复杂度 | 空间复杂度 |
|------|-----------|-----------|
| 存储所有激活值 | $O(N)$ | $O(N)$ |
| 不存储，反向时重算 | $O(N^2)$ | $O(1)$ |
| **存 $\sqrt{N}$ 个检查点** | $O(N\sqrt{N})$ | $O(\sqrt{N})$ |

直觉：存所有激活值太费显存，一个不存太费时间。在中间设 $\sqrt{N}$ 个检查点，反向时只重算相邻检查点之间的部分——时间和空间达到了一个实用平衡。Llama 3 实际使用的是选择性的逐层激活检查点。

## 实践中的扩展路线图

![扩展路线图](/images/lec11_scaling_recipe.png)

这是 Justin 给出的经验法则，非常实用：

| 场景 | 条件 | 策略 |
|------|------|------|
| 起步 | ≤ 128 GPU, ~1B 参数 | **纯 DP** |
| 模型大了 | > 1B 参数 | **DP → FSDP** |
| 显存不够（激活值） | 大 batch / 长序列 | **开激活检查点** |
| GPU 多了 | > 256 GPU | **FSDP → HSDP** |
| 超大模型 | > 1000 GPU, > 50B 参数或 seq > 16K | **+ CP / PP / TP** |

一个重要经验：始终让单 GPU 的 batch size 撑满显存。batch size 太小会浪费算力，太大才考虑激活检查点。

## MFU：衡量分布式训练效率的唯一指标

并行策略多了，怎么判断配置是否合理？业界用 **MFU（Model FLOPs Utilization，模型浮点运算利用率）**。

![MFU](/images/lec11_mfu.png)

$$\text{MFU} = \frac{\text{FLOPs}_{\text{theoretical}} \div \text{peak\_FLOPs\_per\_sec}}{\text{actual\_iteration\_time}}$$

FLOPs_theoretical 是前向+反向传播中所有矩阵乘法的理论浮点运算量（忽略归一化、激活函数等非矩阵乘法操作）。MFU 衡量的是"GPU 理论峰值算力中有多大比例花在了有用的模型计算上"。

| MFU | 评价 |
|-----|------|
| > 30% | 不错 |
| > 40% | 优秀 |

一些公开的 MFU 数据：GPT-3（175B）21.3%，MT-NLG（530B）30.2%，Gopher（280B）32.5%，PaLM（540B）**46.2%**。

一个反直觉的现象：**H100 的 MFU 有时比 A100 还低**。因为 H100 的峰值算力涨了 3.1 倍，但显存带宽只涨了 2.1 倍——归一化、softmax、优化器更新这些内存密集型操作成了新的瓶颈。

## 上下文并行 (CP)

![上下文并行](/images/lec11_context_parallel.png)

当序列长到一张 GPU 处理不了时（比如 131K tokens），需要用上下文并行。思路是：用多张 GPU 联合处理一个长序列。

Transformer 各层的并行化难度不同：

| 层类型 | 难度 | 做法 |
|--------|------|------|
| LayerNorm / 残差连接 | 简单 | 各 GPU 独立处理自己的 token |
| MLP / QKV 投影 | 容易 | 按序列维度并行，像 DP 一样同步梯度 |
| **注意力** | 困难 | 每个 query 要关注所有 key/value |

注意力层的两种策略：

**环形注意力（Ring Attention）**：每个 GPU 拥有一段 query，在 GPU 之间循环传递 K/V 块，逐步累加部分注意力。可以支持极长序列，但实现复杂。

**尤利西斯（Ulysses）**：按注意力头切分，而不是按序列切分。更简单，但最大并行度受限于注意力头数。

实践中，Llama 3 训练的第一阶段用 8K 序列长度不开启 CP，第二阶段扩展到 131K 序列时才启用 CP。

## 流水线并行 (PP)

流水线并行的思路是把模型的不同层分配给不同 GPU。直观但有一个致命问题：**顺序依赖——后面的 GPU 必须等前面的 GPU 算完**，大量时间在空闲。

这种空闲叫做 **Bubble（气泡）**。N 路流水线并行的最大 MFU 只有 $1/N$——4 路就只有 25%。

![流水线并行微批次](/images/lec11_pipeline_microbatch.png)

**解决方案：微批次（microbatch）**。把一个 mini-batch 切成多个小块，让它们依次在 GPU 间流动。前面的微批次算完前向就开始反向，后面的微批次接上来——bubble 被填满了。

4 路 PP + 4 个微批次：MFU 从 25% 提升到 **57.1%**。微批次越多，bubble 占比越小。但代价是：更多微批次意味着更多激活值同时存在，需要更激进的激活检查点策略。

经验法则：微批次数量应远大于 PP 路数（$\text{num\_microbatches} \gg \text{PP\_size}$）。

## 张量并行 (TP)

![张量并行](/images/lec11_tensor_parallel.png)

张量并行把一层内的权重矩阵切分到多个 GPU 上，用分块矩阵乘法并行计算。

以 4 路 TP 为例：权重矩阵 $W$ 按列切成 $[W_1 | W_2 | W_3 | W_4]$，每个 GPU 计算 $Y_i = X W_i$（$X$ 是完整输入）。

单个 TP 层的问题：前向结束后需要 gather 所有 $Y_i$ 拼成完整输出，这个 gather 无法与计算重叠。

**巧妙的 trick：连续两个 TP 层配对。** 第一层按列切分（column-parallel），第二层按行切分（row-parallel）：

$$Y_i = X W_i \quad (\text{各 GPU 独立计算})$$
$$Z = Y_1 U_1 + Y_2 U_2 + Y_3 U_3 + Y_4 U_4 \quad (\text{各 GPU 计算后直接求和})$$

这样中间结果 $Y_i$ 不需要 gather——第二层的输出 $Z$ 直接通过求和得到，隐式完成了通信。这就是为什么 TP 总是成对出现的原因。

**TP 通信量大但粒度细——最适合限制在单台服务器内部（NVLink 900GB/秒）。**

---

## ND 并行：四面开花

![ND 并行](/images/lec11_nd_parallel.png)

对于最大的模型，四种并行策略同时使用：

$$N_{\text{total}} = n_{\text{DP}} \times n_{\text{PP}} \times n_{\text{CP}} \times n_{\text{TP}}$$

每个 GPU 有一个 4D 坐标，同时参与多个并行组。

Llama 3-405B 的实际配置：

| GPU 数 | TP | CP | PP | DP | 序列长度 | MFU |
|--------|----|----|----|----|---------|-----|
| 8,192 | 8 | 1 | 16 | 64 | 8,192 | **43%** |
| 16,384 | 8 | 1 | 16 | 128 | 8,192 | **41%** |
| 16,384 | 8 | 16 | 16 | 8 | 131,072 | **38%** |

规律：
- GPU 翻倍，MFU 略降——新增的 GPU 大部分进了 DP（通信慢）
- 长序列更吃 MFU——环形注意力替代了 FSDP 的快速 all-reduce，通信模式变了

## 总结

这节课把"在几万张 GPU 上训练千亿参数模型"这件事拆解得非常清晰：

1. **硬件是约束**：GPU 内部带宽 3TB/秒，节点间只有 50GB/秒——所有并行策略本质上是在"绕开这个带宽鸿沟"
2. **FSDP + 激活检查点能走很远**：对大多数场景，这两个就够了
3. **超大规模才需要 CP/PP/TP**：每种策略解决不同维度的瓶颈
4. **MFU 是裁判**：策略好不好，不看理论、不看感觉，看 MFU
5. **Llama 3 的 43% MFU 已经是顶级水平**——在 8192 张 H100 上把近一半的算力用在有效计算上，这背后是大量工程优化
